# MRS Module (C++ port of the mrs_plugin)

Back to the index: [../PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md).

Branch `wip/mrs_module`: the Python `mrs_plugin` of mariadb-shell-plugins becomes a built-in C++ module in `modules/mrs/`. The MariaDB REST Service is managed only through REST SQL statements (`CREATE REST SERVICE ...`), which the shell intercepts with its SQL handler mechanism and runs against the metadata schema `mariadb_rest_service` (or a prefixed/postfixed one, see "Metadata schema name") instead of sending them to the server. The `mrs` global object has no functions of its own (only `help`; `runScript` was removed on 2026-10-08, since `\source` and `--sql -f` run REST SQL files); plugins add theirs (the mrs_plugin: SDK generation, project dump/load, `mrs.dump.service`, `mrs.load.service`, `mrs.load.contentSet`). The `core/` part is written so it can later be reused in a MariaDB server plugin: the grammar is bison (as `sql_yacc.yy`), and nothing in `core/` includes shell headers.

## Design decisions

- **Bison, not ANTLR.** `%skeleton "lalr1.cc"`, `api.value.type variant`, `api.token.constructor`, `parse.error verbose`, `%expect 0`. The only ambiguity of the ANTLR grammar (`@NOCHECK` is both a field value option and a CRUD option) is resolved by precedence towards the value option, as ANTLR's greedy matching did. Bison ≥ 3.6 is needed (all CI legs have 3.7+; `cmake/bison.cmake` still says 3.0.4 for the MySQL grammars).
- **Keywords used as names.** Data mapping keys/values may be keywords (`name: name`, `type: type`); keyword tokens carry no value, so the driver remembers the text of the last 8 tokens by position (`Driver::token_text`). Elsewhere keywords must be quoted as names (`"mike"@"MRS"`, `'MySQL'`), exactly as in the ANTLR grammar.
- **SQL modes.** `ANSI_QUOTES` and `NO_BACKSLASH_ESCAPES` change how the lexer unquotes (no backslash escapes in back ticks, nor in `"..."` under ANSI_QUOTES, as in the server). Whether `"..."` is a text or an identifier is checked in the grammar actions (`require_ansi_quotes`), mirroring the ANTLR grammar's `isSqlModeActive(AnsiQuotes)` predicates; rules that take either (`text_or_identifier`, data mapping keys, `@DATATYPE`) accept it in every mode. JSON values keep their source text (`Quoted::raw`), so JSON escapes are not SQL-unescaped.
- **Grammar parity with ANTLR (2026-10-08).** A parser-by-parser comparison found no statement-level differences, only lexical ones. Accidental ones were fixed in bison (double quotes per SQL mode, digit-only request path segments and hex/binary literals rejected, SERVICE required before SCHEMA in GRANT/REVOKE targets, comments ending at `\r`, unterminated and `/*!` comments rejected, `.5` stored as `0.5` in JSON). Deliberate ones were ported to `MRSLexer.g4`/`MRSParser.g4` in mariadb-shell-plugins (extra semicolons, server-style back tick quoting, `FILES` keyword usable as a name, `name@app` without a space, `_` as a name, signed/decimal JSON numbers, `@DATATYPE('...')`), and the plugin's Python parser was regenerated. Remaining: bison rejects a quoted request path without `/` while parsing (ANTLR left that to the listener), skips control characters as whitespace and accepts characters beyond U+FFFF. Test: `Mrs_parser.antlr_compatible_lexical_rules`.
- **Executor results.** `Statement_result` = the dict the Python executor appended (`message`, `affectedItemsCount`, columns/rows, warnings; the Python `id`, operation name, statement index, line and sqlstate are not kept, nothing read them). The shell converts it to the `Custom_result_set` the Python `get_shell_result` produced; `sqlstate` is deliberately left out of error dicts (the shell appends it to the message otherwise). The executor stops at the first failing statement.
- **Per-session state.** `USE REST SERVICE/SCHEMA` lives in `Executor_state`, kept by the `mrs` object per session object (`std::map<weak_ptr<ShellBaseSession>, ...>`, entries of closed sessions dropped; connection ids repeat across servers). It also holds the `Metadata_check` cache: before parsing, `metadata::read_fingerprint()` reads sql_mode, schema version and `MAX(audit_log.id)` in one query; `Ddl_executor::check_metadata()` runs the full schema check only when the version changed and re-validates the current service/schema only when the audit id changed (every service/schema change writes the audit log; a redeploy changes the version). CONFIGURE REST METADATA resets the cache. One query per REST statement instead of about five; tested in `mrs_services_norecord.py` (other session drops the current service, changes the version view).
- **Metadata deployment (schema 5.0.0, UUID ids).** `CONFIGURE REST METADATA` follows the Python `configure()`: refuse a newer major or a too old one without `UPDATE IF AVAILABLE`, skip an available update unless asked, otherwise deploy with backup. The deployment goes through msm's `msm.deploySchema(schema_project_path=<bundled project>, backup=True, session=..., substitutions={schema_prefix, schema_postfix})` when the msm plugin is loaded (options in snake_case; camelCase is rejected), else through `Script_deployer`, which behaves the same and writes the same `plugin_data/msm_plugin/msm_schema_update_log.txt` and backups. A server plugin would pass its own deployment script folder and log/backup hooks. 5.0.0 is the first release of `mariadb_rest_service` (4.1.6, MySQL's version, and its update path were dropped on 2026-10-09: nothing was ever installed under the new name); the REST statements need 5.x. `mysql_tasks` is never deployed (MariaDB only).
- **Ids are UUID text** since 5.0.0: `Id` holds e.g. `31000000-0000-0000-0000-000000000000`, SQL gets it as a bound text value (`sql::Value::id`, NULL when empty), results report it as is (the Python plugin's `convert_id_to_string` does the same). Content files stay `0x...` hex literals (`sql::hex`).
- **SHOW CREATE output** matches the Python formats, with two deliberate additions: `ITEMS PER PAGE` (when not 25) and `COMMENT` on REST SCHEMA statements, so that a dump round-trips.
- **Area ports (db_objects, auth, content) were done by three parallel agents** against fixed header contracts; their deliberate deviations from Python are listed below under State.
- **Password hashing** for MRS users is done in the core (own SHA-256/HMAC/PBKDF2/base64, no OpenSSL), bit-identical to the Python `cypher_auth_string` (`$A$005$salt$key`, 5000 iterations).
- **Content is stored as `0x...` hex literals**, so file bytes never pass through the connection charset. Script analysis (`LOAD [TYPESCRIPT] SCRIPTS`) only stores the flags; no TypeScript parsing.
- **The `mrs` object is extensible.** It is a registered `Extensible_object` created before plugins load, so the Python registrar's `@plugin class mrs` and `@plugin_function("mrs.<name>")` add members to it (Python, CLI and `mrs.help()`); the plugin's own docstring is ignored then. The mrs_plugin keeps the SDK generation and the dumping/loading of MRS projects this way. Since 2026-10-08 the plugin registers no `MRS` SQL handler (its `script.py` handler was removed, uncommitted in mariadb-shell-plugins), so both load together (the `--disable-modules=mrs` option added for the old conflict was removed again); its pytest (248 passed) and grammar test pass against the built-in handler. Test: `mrs_plugin_extension_norecord.py`.
- **Service lookups** keep the Python semantics: a path without developers matches only a service that is not in development; developers are compared through the metadata's `sorted_developers` column (`GROUP_CONCAT ... ORDER BY item`, so sorted case-insensitively).

## Gotchas

- An installed Python `mrs_plugin` (in `~/.mariadb-shell/plugins`) clashes with the built-in module: "An SQL Handler named 'MRS' already exists" and "Could not register plugin object 'mrs'". Test with `MARIADB_SHELL_USER_CONFIG_HOME` pointing at an empty directory.
- The `NULL` keyword cannot be an enum member (`NULL` macro); the keyword enum uses the token names (`NULL_SYMBOL`).
- The generated parser sets `yynerrs_` without reading it: `-Wno-unused-but-set-variable` on the generated file (`-Werror` build).
- **GRANT/REVOKE commit implicitly**, so `Db_transaction` cannot undo a db_object insert when its grants fail. CREATE REST VIEW/PROCEDURE/FUNCTION delete the new object again on a grant failure (`run_grants_of_new_object`); ALTER re-grants and reports a missing routine/table (1305/1146) as a warning, because objects created with FORCE may name one.
- **The metadata procedures run with the `ONLY_FULL_GROUP_BY` mode they were created with.** On MariaDB `table_columns_with_references` then returns no rows for views that group loosely (sakila `film_list`); `get_table_columns_with_references` falls back to a plain INFORMATION_SCHEMA.COLUMNS query in the session's mode. The Python plugin had the same gap.
- **`Custom_result` drops the column names of an empty result** (it only builds metadata when `data` has rows). Tests check `get_column_names()` on non-empty results only.
- **The sandbox on port 3360** (left by an earlier session, sakila loaded, used via `MYSQL_PORT=3360`) still has 4.1.6 metadata under the old name `mysql_rest_service_metadata`, which the module no longer recognizes; the scripted tests deploy their own sandboxes. Do not change it without asking.
- **A stored data mapping holds every column**: columns left out of the mapping are disabled fields (`enabled` false) in `FORMAT=JSON`.
- **The SQL handler is registered once per process** while the shell can be recreated (the test harness does): the callback goes to the last registered `Mrs` through a weak pointer (`active_mrs()`), never to a destroyed one. Capturing `this` crashed once the handler touched the shell core.
- **A crashed scripted test leaves its sandbox running** in `$TMPDIR/<port>` on a reserved test port (3370...), and the next run refuses to start ("mysqld running on port reserved for sandbox tests"); stop that process and remove the folder.
- **MariaDB sends UUID columns with the BINARY flag** but a utf8mb4 collation; `Shell_db_session` treats a value as binary only with the binary collation (63), otherwise UUID ids would come back marked binary.
- **The REST SQL grammar has no host part** in service paths (`developers@/path` only); services created by REST SQL use the empty `url_host` the metadata script inserts.
- **`IRow::get_string` refuses DECIMAL** (e.g. `SUM()`); `Shell_db_session` uses `get_as_string` for all non-string types.
- **`--sql -e` output without a terminal is tab separated**, not a table; scripted tests that call `testutil.call_mysqlsh` expect `a\tb` lines.
- **Option JSON text differs** between the core's compact dump (`{"a":1}`) and the server's (`{"a": 1}`); tests compare with `json.loads`.
- `shell.help('mrs')` does not work in `-e` mode for any object; use `mrs.help()` or `\? mrs`.
- A `grep` with an empty file argument reads stdin and hangs a tool call (`f=$(...)` that found nothing).
- The scripted tests need a sandbox-capable `mariadbd` on `PATH` (`/opt/homebrew/bin/mariadbd` here) and `run_unit_tests` needs `MYSQL_PORT` of a running server plus `MYSQLSH_TEST_HOME=$PWD/unittest`. A sandbox for that: `build/bin/mariadb-shell --py -e "sandbox.deploy(3360, {'password': '', 'sandboxDir': '<scratch>', 'ssl': False})"`.

## No client files in REST SQL (2026-10-09)

- A server plugin cannot read the client's files, so every statement that read or wrote files is gone: `CREATE REST CONTENT SET ... FROM '<dir>' [IGNORE]`, `CREATE REST CONTENT FILE ... FROM '<file>'`, `DUMP REST SERVICE`, `LOAD REST SERVICE` (tokens `DUMP`, `ZIP`, `SCRIPT`, `SQL` removed; prefixes now 11). Content files are inline only: `[BINARY] CONTENT '<text|base64>'`. The dump is `SHOW CREATE REST SERVICE ... INCLUDING DATABASE [AND STATIC [AND DYNAMIC]] | ALL ENDPOINTS` (`Endpoint_selection` in `Show_create_rest_service`). The mrs_plugin does the file work (`mrs.dump.service`, `mrs.load.service`, `mrs.load.contentSet`).
- `LOAD [TYPESCRIPT] SCRIPTS` only on ALTER REST CONTENT SET (`alter_rest_content_set_options`): `metadata::register_scripts` (`core/mrs_scripts.{h,cc}`, C++ port of the plugin's `update_scripts_from_content_set`) analyses the stored `.ts`/`.mts` files (comments/strings blanked, bracket matching, no `std::regex`), registers a SCRIPT_MODULE schema per `@Mrs.module` and a SCRIPT db_object per `@Mrs.script`/`@Mrs.trigger`, links them in `content_set_has_obj_def`, writes `contains_mrs_scripts`, `mrs_scripting_language`, `script_module_files`, `script_definitions` to the set options, and makes every file outside the static folders (`static`, `assets`, `media`, `web`, `js`, `css`, `images`) private (enabled = 2). Re-running replaces earlier registrations (`delete_registered_scripts`).
- SHOW CREATE REST CONTENT SET writes the set (generated options stripped), its files, then `ALTER REST CONTENT SET ... LOAD TYPESCRIPT SCRIPTS;` for SCRIPTS sets.
- Trap (MariaDB 1442): `DELETE FROM db_schema WHERE id NOT IN (SELECT ... FROM db_object)` fails because the db_schema trigger deletes db_object rows; select the ids first, then delete by list. This also fixed DROP REST CONTENT SET on script sets.
- Tests: `mrs_parser_t.cc` (`no_client_file_statements`), `mrs_content_norecord.py` (inline content, script registration), `mrs_services_norecord.py`/`mrs_db_objects_norecord.py` (dump via SHOW CREATE, file run via `testutil.call_mysqlsh --sql -f`), grammar test. 69 pass.

## Metadata schema name (2026-10-09)

- **Rename.** The metadata schema is `mariadb_rest_service` (was `mysql_rest_service_metadata`), its roles `mariadb_rest_service_{admin,schema_admin,dev,user,meta_provider,data_provider}`. MySQL's async-task feature (the mysql_tasks schema, a MySQL HeatWave feature) was dropped on 2026-10-09: no `mysql_task_user` role, no `mysqlTask` option handling (a REST routine's crud_operations are CREATE only), no task sections in the client SDK docs; the mrs_plugin SDK lost `start()`/`watch()`/`kill()` and the task options (mariadb-shell-plugins-23). The MySQL HeatWave exclusion lists in `modules/util/common/dump/constants.h` and the util dump tests keep the MySQL names on purpose.
- **Prefix/postfix.** A metadata schema may be `<prefix>mariadb_rest_service<postfix>` (prefix: letter or `_`, then `[A-Za-z0-9_]`; postfix: `_` then `[A-Za-z0-9_]`; `metadata::schema_name_parts()`, `check_metadata_schema_name()`), e.g. one per cloud customer on one server. Roles: prefix + `mariadb_rest_service_<role>` + postfix (`metadata::role_name(session, role)`), derived from the schema name, so the postfix goes at the end of every name (a comment in the middle of a name splits it when the script runs unsubstituted).
- **Scripts are schema-agnostic.** No schema qualifier in any development section (routines, triggers, views, events and dynamic SQL resolve unqualified names to their own schema; `GRANT ... ON tbl` / `ON *` after `USE` target the current schema); only `CREATE SCHEMA`, `USE` and the role names carry `/*<msm:schema_prefix>*/...` `/*<msm:schema_postfix>*/` (comments: whitespace when run as is). The Workbench audit-trigger generator emits unqualified names. `140-10_tables.sql` is sourced with `[693:-115]`: the offsets count characters of its header/footer, recompute them when the header changes.
- **MSM feature (msm_plugin, mariadb-shell-plugins).** `msm.project.json` declares `"substitutions": {name: {default, pattern}}`; `schemaName` may be a template (`/*<msm:schema_prefix>*/mariadb_rest_service/*<msm:schema_postfix>*/`). `msm.deploySchema(..., substitutions={...})` validates the values (`[A-Za-z0-9_]*` always, plus the pattern), replaces every `/*<msm:name>*/` before splitting the script (undeclared names fail), and uses the effective name for checks, backups, log and the lock (`CONCAT('MSM_METADATA_LOCK', '_', MD5(schema))`, per schema). Templates use `${schema_identifier}` (unquoted template name or backticked plain name) and unqualified names; the deployment template's `msm_create_or_update` uses `DATABASE()`. A single release is deployed with a copy of its version script, which carries the development file's section 910 version: set the development version to the release version before `prepare_release`.
- **Core.** Every statement goes through `Db_session::bind()` (public `query`/`execute`, protected `do_query`/`do_execute`), which replaces `sql::k_metadata_schema_marker` (`` `{metadata_schema}` ``, what `sql::metadata_table()` and the fixed SQL texts use) with `Db_session::metadata_schema()`; values never get the replacement. `Script_deployer` deploys the session's metadata schema (`apply_schema_substitutions()` fills the placeholders); the shell's `Msm_plugin_deployer` passes them as msm substitutions; backups are named after the schema.
- **Resolution.** `Executor_state::metadata_schema` (chosen by `USE REST METADATA SCHEMA` or `CONFIGURE REST METADATA SCHEMA`), else `metadata::resolve_metadata_schema()`: `mariadb_rest_service` if visible, else the only candidate, else (none) the default; several → error listing them. Candidates: `INFORMATION_SCHEMA.SCHEMATA` names containing the base once with valid parts and an `msm_schema_version` view (visible through privileges of *active* roles only: make the MRS role the default role). Resolved once per session (`Metadata_check::schema`) and again on a full check; switching clears the current service/schema. CONFIGURE, SHOW REST METADATA STATUS, USE REST METADATA SCHEMA and SHOW REST METADATA SCHEMAS skip the per-statement check; STATUS fails on ambiguity, the others don't.
- **REST SQL.** `CONFIGURE REST METADATA [SCHEMA name] ...` (`metadataSchema` in `restMetadataOptions`), `USE REST METADATA SCHEMA name`, `SHOW REST METADATA SCHEMAS` (`schema_name, version, current`), `metadata_schema` as last column / JSON key of `SHOW REST METADATA STATUS`. Both grammars and `rest-metadata.md` updated, diagrams regenerated; `configuring-mrs.md` has "One Metadata Schema per Customer".
- **Not done:** the MariaDB REST Daemon (not in these repos) still needs a setting for the metadata schema name and must derive the role names the same way.
