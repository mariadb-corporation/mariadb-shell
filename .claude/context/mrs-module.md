# MariaDB REST Service in the shell (C++ port of the mrs_plugin)

Back to the index: [../PROJECT_CONTEXT.md](../PROJECT_CONTEXT.md).

The Python `mrs_plugin` of mariadb-shell-plugins becomes built-in C++: the core library in `mysqlshdk/libs/mrs/` and the shell integration in `src/mysqlsh/mrs/`. The MariaDB REST Service is managed only through REST SQL statements (`CREATE REST SERVICE ...`), which the shell intercepts with its SQL handler mechanism and runs against the metadata schema `mariadb_rest_service` (or a prefixed/postfixed one, see "Metadata schema name") instead of sending them to the server. The shell creates no `mrs` global object: the mrs_plugin defines it (`@plugin class mrs`, whose docstring is its help) with what REST SQL does not cover (SDK generation, project dump/load, `mrs.dump.service`, `mrs.load.service`, `mrs.load.contentSet`). REST SQL files run through `\source` and `--sql -f`. The core library is written so it can later be reused in a MariaDB server plugin (or extracted as a separate library): the grammar is bison (as `sql_yacc.yy`), and nothing in `mysqlshdk/libs/mrs/` includes shell headers.

## Design decisions

- **Bison, not ANTLR.** `%skeleton "lalr1.cc"`, `api.value.type variant`, `api.token.constructor`, `parse.error verbose`, `%expect 0`. The only ambiguity of the ANTLR grammar (`@NOCHECK` is both a field value option and a CRUD option) is resolved by precedence towards the value option, as ANTLR's greedy matching did. Bison ≥ 3.6 is needed (all CI legs have 3.7+; `cmake/bison.cmake` still says 3.0.4 for the MySQL grammars).
- **Keywords used as names.** Data mapping keys/values may be keywords (`name: name`, `type: type`); keyword tokens carry no value, so the driver remembers the text of the last 8 tokens by position (`Driver::token_text`). Elsewhere keywords must be quoted as names (`"mike"@"MRS"`, `'MySQL'`), exactly as in the ANTLR grammar.
- **SQL modes.** `ANSI_QUOTES` and `NO_BACKSLASH_ESCAPES` change how the lexer unquotes (no backslash escapes in back ticks, nor in `"..."` under ANSI_QUOTES, as in the server). Whether `"..."` is a text or an identifier is checked in the grammar actions (`require_ansi_quotes`), mirroring the ANTLR grammar's `isSqlModeActive(AnsiQuotes)` predicates; rules that take either (`text_or_identifier`, data mapping keys, `@DATATYPE`) accept it in every mode. JSON values keep their source text (`Quoted::raw`), so JSON escapes are not SQL-unescaped.
- **Grammar parity with ANTLR.** The two grammars agree statement by statement; lexically, bison and `MRSLexer.g4` both take extra semicolons, server-style back tick quoting, `FILES` as a name, `name@app` without a space, `_` as a name, signed/decimal JSON numbers and `@DATATYPE('...')`, and both reject digit-only request path segments, hex/binary literals in paths, SCHEMA without SERVICE in GRANT/REVOKE targets, unterminated and `/*!` comments. Remaining differences: bison rejects a quoted request path without `/` while parsing (ANTLR left that to the listener), skips control characters as whitespace and accepts characters beyond U+FFFF. Test: `Mrs_parser.antlr_compatible_lexical_rules`. Grammar changes go into both, and the plugin's Python parser is regenerated from the `.g4` files.
- **Executor results.** `Statement_result` = the dict the Python executor appended (`message`, `affectedItemsCount`, columns/rows, warnings; the Python `id`, operation name, statement index, line and sqlstate are not kept, nothing read them). The shell converts it to the `Custom_result_set` the Python `get_shell_result` produced; `sqlstate` is deliberately left out of error dicts (the shell appends it to the message otherwise). The executor stops at the first failing statement.
- **Per-session state.** `USE REST SERVICE/SCHEMA` lives in `Executor_state`, kept per session object (`std::map<weak_ptr<ShellBaseSession>, ...>`, entries of closed sessions dropped; connection ids repeat across servers). It also holds the `Metadata_check` cache: before parsing, `metadata::read_fingerprint()` reads sql_mode, schema version and the audit log mark (`Audit_log_mark`: `MAX(id)` and `COUNT(*)`; ids are not in commit order, so a late commit with a lower id, e.g. on Galera with several write nodes, only shows in the count) in one query; `Ddl_executor::check_metadata()` runs the full schema check only when the version changed and re-validates the current service/schema only when the audit mark changed (every service/schema change writes the audit log; a redeploy changes the version). CONFIGURE REST METADATA resets the cache. One query per REST statement instead of about five; tested in `mrs_services_norecord.py` (other session drops the current service, changes the version view).
- **Versions: shell and plugins ship aligned** (the release process gives both the same version). 26.10.2 is the first shell with the built-in REST SQL handler; the mrs_plugin from then on has no handler of its own and needs it (code_ext's `MINIMUM_SHELL_VERSION` is 26.10.2), and msm from 26.10.2 takes `substitutions`.
- **Metadata deployment (schema 5.0.0, UUID ids).** `CONFIGURE REST METADATA` follows the Python `configure()`: refuse a newer major or a too old one without `UPDATE IF AVAILABLE`, skip an available update unless asked, otherwise deploy with backup. The deployment goes through msm's `msm.deploySchema(schema_project_path=<bundled project>, backup=True, session=..., substitutions={schema_prefix, schema_postfix})` when the msm plugin is loaded and is 26.10.2 or later (`msm.version()`; earlier ones do not take `substitutions`, so the shell deploys itself) (options in snake_case; camelCase is rejected), on a connection of its own (msm runs the script on its session: `USE`, FK/unique checks, `sql_mode`; msm switches the global session only for its dump/load, under the shared lock), else through `Script_deployer`, which behaves the same and writes the same `plugin_data/msm_plugin/msm_schema_update_log.txt` and backups. The schema backup dumps and loads on the target session (`Dump_schema_backup`). A server plugin would pass its own deployment script folder and log/backup hooks. 5.0.0 is the first release of `mariadb_rest_service` (MySQL's 4.1.6 and its update path are not carried: nothing was ever installed under the new name); the REST statements need 5.x. `mysql_tasks` is never deployed (MariaDB only).
- **Ids are UUID text** since 5.0.0: `Id` holds e.g. `31000000-0000-0000-0000-000000000000`, SQL gets it as a bound text value (`sql::Value::id`, NULL when empty), results report it as is (the Python plugin's `convert_id_to_string` does the same). Content files stay `0x...` hex literals (`sql::hex`).
- **Round trips.** Every statement goes through bound values (`Statement`/`Delete`/`Where`, mode-aware quoting; `Mrs_sql` gtest and the NO_BACKSLASH_ESCAPES case in `mrs_services_norecord.py`). `metadata::new_id()` takes ids from `Db_session::id_pool`, fetched in batches of 1, 2, 4 ... 64 with a recursive CTE; the objects, references and fields of a rest_object are inserted with three multi-row INSERTs (`insert_objects`) and read with one fields query per rest_object (CREATE REST VIEW over 40 columns with a reference: about 20 client queries). `clone_content_set` copies the files with one `INSERT ... SELECT` on the server (ids from the `UUID_v7()` default; tested byte for byte in `mrs_content_norecord.py`).
- **SHOW CREATE output** matches the Python formats, with two deliberate additions: `ITEMS PER PAGE` (when not 25) and `COMMENT` on REST SCHEMA statements, so that a dump round-trips. `SHOW CREATE REST SERVICE ... INCLUDING ... ENDPOINTS` names the service once (CREATE, then `USE REST SERVICE <full path>;`); roles, schemas, objects (`ON SCHEMA /s`), content sets/files (`ON CONTENT SET /cs`) and the LOAD SCRIPTS ALTER are written without `ON SERVICE` (`on_current_service` flag on the writers; standalone SHOW CREATE writes it), so `as_path` of `mrs.load.service` rewrites only those two statements. `sql::quote` doubles `'` and keeps line breaks and `"` raw; content files holding a backslash, NUL or Ctrl-Z are written as `BINARY CONTENT` (`is_plain_text`), so content dumps read the same with `NO_BACKSLASH_ESCAPES`. A backslash in other strings (comments) still needs `\\`.
- **View field annotations round-trip.** `field_attributes` writes them in grammar order (mode, value options, `@DATATYPE`, CRUD, `JSON SCHEMA` compact), `@UNNEST` comes first on a reference, and a view field gets `@DATATYPE` only when it differs from its column's live `COLUMN_TYPE` (`Datatype_check`, one INFORMATION_SCHEMA query per table); a routine's RESULT fields always get it. A lone `@NOCHECK` on a reference, which the grammar parses as a value option, is taken as the reference's (`apply_reference`). Test: the `/payment` case in `mrs_rest_objects_norecord.py`.
- **Password hashing** for MRS users is done in the core with OpenSSL (SHA-256, PBKDF2, salt from `RAND_bytes`), bit-identical to the Python `cypher_auth_string` (`$A$005$salt$key`, 5000 iterations): an incremental `Sha256` and an `Hmac_sha256` whose pads are hashed once; cross-checked against Python `hashlib` in `mrs_auth_norecord.py`.
- **Content is stored as `0x...` hex literals**, so file bytes never pass through the connection charset. Script analysis (`LOAD [TYPESCRIPT] SCRIPTS`) only stores the flags; no TypeScript parsing.
- **Placement.** The core is a library in `mysqlshdk/libs/mrs/` (like the bison `libs/yparser` and the ANTLR `libs/parser` with its grammars), with its data (`db_schema/`, `antlr_grammar/`) and tests (`unittest/mysqlshdk/libs/mrs/`), so extracting it later moves one folder; it must not include shell headers. The shell integration (`rest_sql_handler`, `shell_db_session`, `schema_deployers`) is in `src/mysqlsh/mrs/`, compiled into `shellfe`, because it needs `ShellBaseSession`, the SQL handler registry and `modules/util` dump/load. `modules/` is only for code that exposes scripting objects. File names follow the class they hold, without an `mrs_` prefix (the folder is the namespace). Includes are `"mysqlshdk/libs/mrs/..."` and `"src/mysqlsh/mrs/..."` (the short `"mysqlsh/..."` form fails: `modules/` includes `mysql_shell.h` without `src/` on its include path).
- **The `mrs` object belongs to the mrs_plugin.** The shell only registers the `MRS` SQL handler; the plugin defines `mrs` as on any shell and registers no SQL handler, so both load together, and the plugin works the same on a shell without the built-in module. Its help is the plugin's `@plugin class mrs` docstring (REST SQL overview + what the plugin adds); the shell registers no help for it. Without the plugin there is no `mrs` global and no `\? mrs` help; `shell.listSqlHandlers()` still lists `MRS`.
- **Service lookups** keep the Python semantics: a path without developers matches only a service that is not in development; developers are compared through the metadata's `sorted_developers` column (`GROUP_CONCAT ... ORDER BY item`, so sorted case-insensitively).

## Gotchas

- An installed Python `mrs_plugin` older than the 5.0.0 rework still registers its own `MRS` SQL handler and clashes with the built-in one ("An SQL Handler named 'MRS' already exists"). Test with `MARIADB_SHELL_USER_CONFIG_HOME` pointing at an empty directory.
- The `NULL` keyword cannot be an enum member (`NULL` macro); the keyword enum uses the token names (`NULL_SYMBOL`).
- The generated parser sets `yynerrs_` without reading it: `-Wno-unused-but-set-variable` on the generated file (`-Werror` build).
- **GRANT/REVOKE commit implicitly**, so `Db_transaction` cannot undo a rest_object insert when its grants fail. CREATE REST VIEW/PROCEDURE/FUNCTION delete the new object again on a grant failure (`run_grants_of_new_object`); ALTER re-grants and reports a missing routine/table (1305/1146) as a warning, because objects created with FORCE may name one.
- **The metadata procedures run with the `ONLY_FULL_GROUP_BY` mode they were created with.** On MariaDB `table_columns_with_references` then returns no rows for views that group loosely (sakila `film_list`); `get_table_columns_with_references` falls back to a plain INFORMATION_SCHEMA.COLUMNS query in the session's mode. The Python plugin had the same gap.
- **`Custom_result` drops the column names of an empty result** (it only builds metadata when `data` has rows). Tests check `get_column_names()` on non-empty results only.
- **A stored data mapping holds every column**: columns left out of the mapping are disabled fields (`enabled` false) in `FORMAT=JSON`.
- **The SQL handler is registered once per process** while the shell can be recreated (the test harness does): the callback goes to the last registered `Mrs` through a weak pointer (`active_mrs()`), never to a destroyed one. Capturing `this` crashed once the handler touched the shell core.
- **A crashed scripted test leaves its sandbox running** in `$TMPDIR/<port>` on a reserved test port (3370...), and the next run refuses to start ("mysqld running on port reserved for sandbox tests"); stop that process and remove the folder.
- **MariaDB sends UUID columns with the BINARY flag** but a utf8mb4 collation; `Shell_db_session` treats a value as binary only with the binary collation (63), otherwise UUID ids would come back marked binary.
- **The REST SQL grammar has no host part** in service paths (`developers@/path` only); services created by REST SQL use the empty `url_host` the metadata script inserts.
- **`IRow::get_string` refuses DECIMAL** (e.g. `SUM()`); `Shell_db_session` uses `get_as_string` for all non-string types.
- **`--sql -e` output without a terminal is tab separated**, not a table; scripted tests that call `testutil.call_mysqlsh` expect `a\tb` lines.
- **Option JSON text differs** between the core's compact dump (`{"a":1}`) and the server's (`{"a": 1}`); tests compare with `json.loads`.
- **`EXPECT_CONTAINS(expected, actual)` iterates `expected`**; with two strings it only checks characters, so it always passes. Use `EXPECT_IN(substring, text)`.
- **Counting queries in the general log** also counts the statements of the metadata triggers (`audit_log` inserts), which are no round trips.
- **`cmake --build bld --target mariadb-shell run_unit_tests` does not refresh the bundled release scripts**; also build `mrs_metadata_project` (or `all`), else CONFIGURE deploys the old release.
- A `grep` with an empty file argument reads stdin and hangs a tool call (`f=$(...)` that found nothing).
- The scripted tests need a sandbox-capable `mariadbd` on `PATH` and run via `npm run rut` (see the index); the MRS suites: `RUT_FILTER="Mrs_*:*mrs_*:*shell_register_sql_handler*:*cmd_help*:*help_norecord*:*plugin_cli_integration*" npm run rut`.

## State

- **All REST SQL statements of the grammar are implemented**, end to end against MariaDB 12.3.2: metadata, services, schemas, views, procedures, functions, auth apps, users, roles, grants, content sets and files. `DUMP/LOAD REST PROJECT` are not in either grammar (syntax errors; projects are the mrs_plugin's `mrs.dump/load.serviceProject()`).
- **Listing statements:** `SHOW REST USERS [(ON|FROM) [SERVICE] path] [FOR AUTH APP name]` (no filter: current service, else all users; `FOR AUTH APP` alone ignores the current service), `SHOW REST AUTH VENDORS`, `SHOW REST SERVICES [FOR AUTH APP name]`; keyword `VENDORS`, usable unquoted as a name (`identifier_keyword`, like `FILES`); metadata `get_auth_vendors`, `get_users(session, service_id?, auth_app_id?)`.
- **For code_ext's MRS GUI** (it reaches the shell only through mcp_plugin's SQL tools): a trailing `FORMAT=JSON` / `FORMAT=TRADITIONAL` (`opt_output_format`; `= json`, `='json'` too; other names fail at parse time with `Unknown REST format name: 'x'`) on every `SHOW CREATE REST ...` statement, which then returns one cell of pretty JSON (`metadata_json`: metadata column names as keys, UUID ids, option columns embedded; views/routines with `data_mappings` -> `fields` -> `data_mapping_reference`; services with auth app names and, with `INCLUDING DATABASE ENDPOINTS`, `rest_schemas` -> `rest_objects`; auth apps with their services, users with roles, roles with privileges; never app secrets, password hashes or file bytes); `SHOW REST COLUMNS FROM [TABLE|VIEW|PROCEDURE|FUNCTION] [schema.]name [FORMAT=JSON]` (rows `position, name, kind, datatype, not_null, is_primary, id_generation, reference`; columns + references from `table_columns_with_references`, or parameters + a `RETURN` row; type detected via `database_object_type` / `routine_exists`; schema defaults to the current REST schema's database, then `DATABASE()`); `metadata_version` (max `audit_log.id`, `Status::metadata_version`) as last column of `SHOW REST METADATA STATUS`. Keywords `TABLE` (only a data-mapping key: as a name it would conflict after `FROM`) and `COLUMNS` (an `identifier_keyword`). FORMAT goes at the end (user's choice; the server puts `FORMAT=JSON` right after `EXPLAIN`).
- **For the MariaDB REST Daemon** (the MySQL Router fork; the user wants DAEMON(S), never ROUTER(S), in REST SQL): `SHOW REST DAEMONS [FORMAT=JSON]` (rows `id, name, address, product_name, version, last_check_in, active, developer`; active = checked in within 10 s; JSON is an array with `attributes`/`options`), `SHOW REST SERVICES FOR DAEMON '<uuid>'` (via the `rest_daemon_services` view), `DROP REST DAEMON [IF EXISTS] '<uuid>'` (deletes `rest_daemon_general_log` and `rest_daemon_status` rows first: their FKs are NO ACTION); keywords `DAEMON`/`DAEMONS` (also names); metadata `Daemon` (`id` is an `Id`), `get_daemons`, `get_daemon`, `get_services_of_daemon`, `delete_daemon`. The daemon id is a quoted UUID (`text_string_literal`, checked and lower-cased by the bison helper `daemon_id()`, `Invalid REST daemon id`). The status column `required_rest_daemon_version` (`k_required_rest_daemon_version`) is 26.10.0. The daemon's side: [rest-daemon-5.0.md](rest-daemon-5.0.md).
- **`SHOW REST [METADATA] STATUS FORMAT=JSON`:** the status plus `available_metadata_versions` (`Schema_deployer::available_versions()`; the shell deployers and `Script_deployer` read `released_versions(dir)`, the files ending in `X.Y.Z.sql`, from the bundled project's `releases/versions` or the deployment folder) and `configuration_options` (`Status::configuration_options`, `config.data`). `get_status` fills `available_metadata_version` and `required_rest_daemon_version` also before the schema exists. Replaces the mrs_plugin's `get.availableMetadataVersions` / `get.configurationOptions`.
- **Tests:** gtest `Mrs_lexer`/`Mrs_parser`, `Mrs_sql`, `Mrs_schema_deployment` (`Script_deployer` on a fake session); scripted `mrs_services`, `mrs_rest_objects`, `mrs_auth`, `mrs_content`, `mrs_grammar_test` (the whole `grammar_test.sql`, no "Failed to"/"Cannot" output), `mrs_metadata_schema` (default and prefixed/postfixed deployments, roles, USE REST METADATA SCHEMA, ambiguity, SHOW REST METADATA SCHEMAS, a tenant account finding its schema); `shell_register_sql_handler` (py+js) covers the built-in `MRS` handler.
- **Deliberate deviations from Python** (fixes of Python bugs or added behaviour): ALTER REST AUTH APP implemented (Python had none); reference options stored per reference (Python stored the parent's); CREATE REST VIEW on a missing table fails; DROP/ALTER only act on their own object kind; ALTER VIEW CLASS without mapping keeps the fields; IDENTIFIED BY only for users with a password; ALTER REST USER honours MERGE OPTIONS; duplicate CONTENT FILE paths rejected (no unique index in the schema); routine PARAMETERS/RESULT always print braces (`{}` when empty) so dumps parse; copy-paste typos in Python messages fixed.
- **Not done:** SDK generation (stays in the mrs_plugin for now), ZIP dumps, a scripted test of a real msm-plugin deployment (the test shells have no msm plugin; a stand-in `msm` global covers the session handoff, msm's own deployment is tested in the plugins repo), MRS script (TypeScript) analysis, `${openApiUi}` content download, a JS-mode test.

## Next steps

1. **One deployment path?** (decision pending, review needed): `make_schema_deployer` uses `msm.deploySchema()` when the msm plugin is loaded, else `Script_deployer`. The msm route is safe for the user's session (own connection; msm switches the global session only for its dump/load, under the shared lock), but the original concerns stand: two implementations of lock/backup/drop-restore to keep in step, and the real msm route is not tested in the shell (only a stand-in `msm` global; msm's own deployment is tested in the plugins repo), plus the msm-version coupling (`substitutions`, only msm 26.10.2+). For keeping it: msm's future deployment logic reaches CONFIGURE REST METADATA. To decide: compare msm's `deploy_schema` with `Script_deployer` for divergences, and whether `Script_deployer` alone is needed anyway (no msm loaded, a server-side build).
2. **Grammar parity** (decision pending): nothing but the docs scripts uses the ANTLR grammar and only lexical parity is tested. Either a CI job parsing `unittest/data/mrs/grammar_test.sql` with ANTLR, or declare the `.g4` files docs-only in `antlr_grammar/README.md`.
3. **`Rest_sql_handler::m_states` has no mutex**: concurrent REST SQL from two threads (plugin threads, MCP server) races on the map. Add a `std::mutex` around its use in `run_rest_sql`.
4. **Shared data provider role: REVOKE ALL takes other objects' privileges** (decision pending, wider fix to implement). Every REST object grants to the one `<prefix>mariadb_rest_service_data_provider<postfix>` role, and privileges are not reference-counted, yet `revoke_all_from_rest_object()` runs `REVOKE ALL ON schema.table` for: DROP REST VIEW/PROCEDURE/FUNCTION (`delete_rest_object`), and the privilege switch of ALTER and CREATE OR REPLACE (`regrant`/`restore_grants` in `ddl_executor_rest_objects.cc`). Dropping or changing one object on a table removes privileges the other REST objects on that table (and on its referenced tables) still need: their endpoints get access denied. Inherited from Python (`update_db_objects`, `delete_db_object`). Only the failed-CREATE cleanup is safe (it deletes the metadata only and revokes nothing; leftover grants of the failed statement stay). Wider fix: after the metadata change, recompute what the role needs on each affected table from the REST objects left (their grant statements, crud_operations, references and explicit `grants` options) and revoke only privileges no object needs; explicit grants make that union harder.
5. **Hand-written JSON parser vs. rapidjson** (decision pending). `json.{h,cc}` keeps the core free of a JSON library (for a possible server plugin; the server tree has no rapidjson, but it is header-only), yet its parser needed fixes (surrogates, nesting depth capped at 512) and still accepts invalid numbers (`-`, `1.`, `1.e`). Option: keep `json::Value` and its `dump` (the SHOW CREATE layout), build it from rapidjson's SAX reader with `kParseIterativeFlag` (rapidjson recurses by default) and `kParseNumbersAsStringsFlag` (numbers keep their text).
6. **Number and literal grammar gaps** (low). `json.cc` `Parser::parse_number` only checks that it consumed something, so `-`, `1.`, `1.e` and `-e` parse as numbers and `dump()` writes them back unchanged: a decorator literal such as `{a: -}` becomes "valid" JSON the server refuses later, far from the cause. Fix: require a digit after an optional `-`, after `.` and after `e[+-]`, else `fail("Invalid number")` (gone if item 5 switches to rapidjson). `lexer.cc` `lex_number` takes `0X…`/`0B…` as hex/binary literals; the server and `MRSLexer.g4` take only lowercase `0x`/`0b`, so `s.0X1F` is an identifier there and a syntax error here. Fix: test `peek(1) == 'x' || peek(1) == 'b'` only. Both want cases in `json_t.cc` / `lexer_t.cc`.
7. **Script modules: options overwritten by the same LOAD SCRIPTS** (edge case). `delete_registered_scripts` (`metadata_content.cc`) finds a content set's trigger-only modules through the module paths in its stored `script_definitions`; `ALTER REST CONTENT SET ... OPTIONS {...} LOAD SCRIPTS` overwrites the options (`update_content_set` in `ddl_executor_content.cc`) before `register_scripts` runs, so a trigger-only module removed in that statement stays as an empty `SCRIPT_MODULE` schema. Harmless leftover. Fix: read the module paths from the content set as it was before `update_content_set` and pass them to `register_scripts`, or keep the generated script options across an OPTIONS change.
8. **Script modules: one REST schema shared by two content sets** (edge case). `register_scripts` reuses an existing `SCRIPT_MODULE` schema found by request path, so two content sets declaring a module at the same path share it; one set's cleanup may then delete it while the other still declares only triggers there (it is recreated on that set's next LOAD SCRIPTS). Fix: record which content set created a module schema (a link table, or an id in the schema's options) and refuse, or report, a module path another content set owns.
9. Open security items (see § Security notes): mask the auth app secret and the password hash in the SQL log and keep `APP SECRET` statements out of the history; harden `rest_daemon_status_downsample` (inherited).
10. `README.md` § Features Not Available still lists "MySQL REST Service (MRS) management"; remove the row and mention the MariaDB REST Service.
11. CI needs bison ≥ 3.6 on every leg (check Windows).
12. Port SDK generation (stays in the mrs_plugin unless decided otherwise; a C++ port would need a home other than a built-in `mrs` object, which doesn't exist).
13. Server plugin / separate library: only if planned; then a `Db_session` over the server's internal API.
14. The mrs_plugin's `_json_document` workaround (mariadb-shell-plugins) is a no-op for `sdk_service_data` output now and can go.

## No client files in REST SQL

- A server plugin cannot read the client's files, so no statement reads or writes files: there is no `CREATE REST CONTENT SET ... FROM '<dir>'`, `CREATE REST CONTENT FILE ... FROM '<file>'`, `DUMP REST SERVICE` or `LOAD REST SERVICE`. Content files are inline only: `[BINARY] CONTENT '<text|base64>'`. The dump is `SHOW CREATE REST SERVICE ... INCLUDING DATABASE [AND STATIC [AND DYNAMIC]] | ALL ENDPOINTS` (`Endpoint_selection` in `Show_create_rest_service`). The mrs_plugin does the file work (`mrs.dump.service`, `mrs.load.service`, `mrs.load.contentSet`).
- `LOAD [TYPESCRIPT] SCRIPTS` only on ALTER REST CONTENT SET (`alter_rest_content_set_options`): `metadata::register_scripts` (`mysqlshdk/libs/mrs/scripts.{h,cc}`, C++ port of the plugin's `update_scripts_from_content_set`) analyses the stored `.ts`/`.mts` files (comments/strings blanked, bracket matching, no `std::regex`), registers a SCRIPT_MODULE schema per `@Mrs.module` and a SCRIPT rest_object per `@Mrs.script`/`@Mrs.trigger`, links them in `content_set_has_rest_object`, writes `contains_mrs_scripts`, `mrs_scripting_language`, `script_module_files`, `script_definitions` to the set options, and makes every file outside the static folders (`static`, `assets`, `media`, `web`, `js`, `css`, `images`) private (enabled = 2). Re-running replaces earlier registrations (`delete_registered_scripts`).
- SHOW CREATE REST CONTENT SET writes the set (generated options stripped), its files, then `ALTER REST CONTENT SET ... LOAD TYPESCRIPT SCRIPTS;` for SCRIPTS sets.
- Trap (MariaDB 1442): `DELETE FROM rest_schema WHERE id NOT IN (SELECT ... FROM rest_object)` fails because the rest_schema trigger deletes rest_object rows; select the ids first, then delete by list.
- Tests: `parser_t.cc` (`no_client_file_statements`), `mrs_content_norecord.py` (inline content, script registration), `mrs_services_norecord.py`/`mrs_rest_objects_norecord.py` (dump via SHOW CREATE, file run via `testutil.call_mysqlsh --sql -f`), grammar test.

## Metadata schema name

- **Name.** The metadata schema is `mariadb_rest_service`, its roles `mariadb_rest_service_{admin,schema_admin,dev,user,meta_provider,data_provider}`. MySQL's async-task feature (the mysql_tasks schema, a MySQL HeatWave feature) is not supported: no `mysql_task_user` role, no `mysqlTask` option handling (a REST routine's crud_operations are CREATE only), no task sections in the client SDK docs, no `start()`/`watch()`/`kill()` in the mrs_plugin SDK. The MySQL HeatWave exclusion lists in `modules/util/common/dump/constants.h` and the util dump tests keep the MySQL names on purpose.
- **Prefix/postfix.** A metadata schema may be `<prefix>mariadb_rest_service<postfix>` (prefix: letter or `_`, then `[A-Za-z0-9_]`; postfix: `_` then `[A-Za-z0-9_]`; `metadata::schema_name_parts()`, `check_metadata_schema_name()`), e.g. one per cloud customer on one server. Roles: prefix + `mariadb_rest_service_<role>` + postfix (`metadata::role_name(session, role)`), derived from the schema name, so the postfix goes at the end of every name (a comment in the middle of a name splits it when the script runs unsubstituted).
- **Scripts are schema-agnostic.** No schema qualifier in any development section (routines, triggers, views, events and dynamic SQL resolve unqualified names to their own schema; `GRANT ... ON tbl` / `ON *` after `USE` target the current schema); only `CREATE SCHEMA`, `USE` and the role names carry `/*<msm:schema_prefix>*/...` `/*<msm:schema_postfix>*/` (comments: whitespace when run as is). The Workbench audit-trigger generator emits unqualified names. `140-10_tables.sql` is sourced with `[695:-115]` in `mariadb_rest_service_next.sql`: the offsets count characters of its header/footer, recompute them when the header changes.
- **MSM feature (msm_plugin, mariadb-shell-plugins).** `msm.project.json` declares `"substitutions": {name: {default, pattern}}`; `schemaName` may be a template (`/*<msm:schema_prefix>*/mariadb_rest_service/*<msm:schema_postfix>*/`). `msm.deploySchema(..., substitutions={...})` validates the values (`[A-Za-z0-9_]*` always, plus the pattern), replaces every `/*<msm:name>*/` before splitting the script (undeclared names fail), and uses the effective name for checks, backups, log and the lock (`CONCAT('MSM_METADATA_LOCK', '_', MD5(schema))`, per schema). Templates use `${schema_identifier}` (unquoted template name or backticked plain name) and unqualified names; the deployment template's `msm_create_or_update` uses `DATABASE()`. A single release is deployed with a copy of its version script, which carries the development file's section 910 version: set the development version to the release version before `prepare_release`.
- **Core.** Every statement goes through `Db_session::bind()` (public `query`/`execute`, protected `do_query`/`do_execute`), which replaces `sql::k_metadata_schema_marker` (`` `{metadata_schema}` ``, what `sql::metadata_table()` and the fixed SQL texts use) with `Db_session::metadata_schema()`; values never get the replacement. `Script_deployer` deploys the session's metadata schema (`apply_schema_substitutions()` fills the placeholders); the shell's `Msm_plugin_deployer` passes them as msm substitutions; backups are named after the schema.
- **Resolution.** `Executor_state::metadata_schema` (chosen by `USE REST METADATA SCHEMA` or `CONFIGURE REST METADATA SCHEMA`), else `metadata::resolve_metadata_schema()`: `mariadb_rest_service` if visible, else the only candidate, else (none) the default; several → error listing them. Candidates: `INFORMATION_SCHEMA.SCHEMATA` names containing the base once with valid parts and an `msm_schema_version` view (visible through privileges of *active* roles only: make the MRS role the default role). Resolved once per session (`Metadata_check::schema`) and again on a full check; switching clears the current service/schema. CONFIGURE, SHOW REST METADATA STATUS, USE REST METADATA SCHEMA and SHOW REST METADATA SCHEMAS skip the per-statement check; STATUS fails on ambiguity, the others don't.
- **REST SQL.** `CONFIGURE REST METADATA [SCHEMA name] ...` (`metadataSchema` in `restMetadataOptions`), `USE REST METADATA SCHEMA name` (a no-op that keeps the current service and schema when name is already the session's chosen schema, as code_ext prefixes every call with it), `SHOW REST METADATA SCHEMAS` (`schema_name, version, current`), `metadata_schema` as last column / JSON key of `SHOW REST METADATA STATUS`. `configuring-mrs.md` has "One Metadata Schema per Customer".
- **Not done:** the MariaDB REST Daemon (not in these repos) still needs a setting for the metadata schema name and must derive the role names the same way.

## sdk_service_data on MariaDB

- MariaDB keeps JSON in SP variables as text, so a `JSON_ARRAY_APPEND(..., x)` of a FETCHed `JSON_OBJECT` nests a string; BIT(1) columns come out as the raw byte. Section 150-20 therefore appends `JSON_EXTRACT(x, '$')` at all four levels and writes every flag as `col = 1` (service `enabled`/`published`, schema/object `requires_auth`/`internal`, field `enabled`/`allow_filtering`/`allow_sorting`/`no_check`/`no_update`), which MariaDB's JSON_OBJECT emits as `true`/`false`.
- **Regenerating a release** with msm (temp config home with only `msm_plugin` symlinked, `shell.options.useWizards = False`): set the development version to the release version first (else section 910 of the release carries the next version), then `msm.prepare_release(schema_project_path=..., version='X.Y.Z', next_version='X.Y.Z+1', overwrite_existing=True)` and `msm.generate_deployment_script(..., version='X.Y.Z', overwrite_existing=True)`, then set the development version back to the next one. The Workbench model has no routines.
- Test: `mrs_rest_objects_norecord.py` chunk "sdk_service_data returns one nested JSON document".

## Security notes

- **GRANT column names are quoted.** `explicit_privilege()` `sql::quote_identifier()`s every `grants[].columnList` name and refuses non-strings or empty names. The grants of *stored* options run again with the privileges of whoever ALTERs the object (`regrant`, `restore_grants`), and LOAD SCRIPTS runs the grants of `@Mrs.script` decorators in stored TypeScript; `_dev`, `_schema_admin` and `_admin` can write both without GRANT OPTION, so unquoted names were an injection. Test chunk "The column names of an explicit grant are quoted" in `mrs_rest_objects_norecord.py`. The mrs_plugin's `get_grant_statements_for_explicit_grants` has the same bug (not fixed there).
- **Landing page query parameters are filtered.** `index.html` takes `service`, `authPath` and `redirectUrl` from the query string and assigns `redirectUrl` to `location.href` after the login: `localPath()` (paths on this server only: no absolute URL, no `//` or `/\` start) and `redirectTarget()` (`http:`/`https:` only; other hosts stay allowed, by decision) filter them where they enter, `oracleCloudAuthLink` uses them too, and `authApp`/`redirectUrl` are encoded in the login URLs.
- **Regenerating the landing page:** `mysqlshdk/libs/mrs/db_schema/prepare_default_static_content.sh` (needs `html-minifier-terser` and `envsubst`; reproduces the committed 140-40 byte for byte from an unchanged page) writes `sections/140-40_default_static_content.sql` and an untracked `config.data.json` (delete it). While 5.0.0 is unreleased, swap the `index.html` base64 in `releases/versions/mariadb_rest_service_5.0.0.sql` and `releases/deployment/...5.0.0.sql` directly (the only difference msm would make; the two stay byte-identical); once released, a change needs a new version. Then build `mrs_metadata_project`.
- **Open:** the auth app secret (`auth_app.access_token`) and the `$A$005$` hash are rendered client-side into the INSERT/UPDATE, which `Log_sql` writes to `mysqlsh.log` when it fails (default `logSql=error`) or always (`logSql=on`); and `CREATE/ALTER REST AUTH APP ... APP SECRET` is not matched by the default `history.sql.ignorePattern`, so it is saved to the history. Fix: wrap those values in `/*((*/ ... /*))*/` when rendering (`mask_sql_query` masks them), and mark the statement unsafe for the history.
- **Inherited from MySQL REST Service 4.1.5:** `rest_daemon_status_downsample` splices names from `rest_daemon.attributes` (writable by `_meta_provider`, i.e. the daemon account) into a PREPAREd statement, and the hourly `rest_daemon_status_cleanup` event runs it as the deploying account. Harden by checking the names against the column list.

## CLONE REST SERVICE copies the whole service

`metadata::clone_service()` (`metadata.cc`), called by `Ddl_executor` for `CLONE REST SERVICE <path> NEW REQUEST PATH [dev@]<path>`, copies in one transaction. Message: `REST SERVICE `/a` cloned to `dev@/a` successfully.`

- **Copied:** the service row, including the columns REST SQL doesn't set (`name`, `parent_id`, `enable_sql_endpoint`, `custom_metadata_schema`); the auth app links with their `options`; schemas and objects (`clone_schema` fills an old-to-new object id map); content sets with `internal` and their files; service roles, parents first with `derived_from` remapped, their privileges (one on the source's `host_ctx` gets the new path) and their user grants (the users of the auth apps are shared); user groups with members, roles and hierarchy; user hierarchy types with `mrs_user_hierarchy`; `mrs_rest_object_row_group_security`.
- **Content-set links** (`content_set_has_rest_object`) move to the copied objects. A link to an object outside the service is not copied, whatever its `kind`: the clone owns only what it created (and a `Script` link's AFTER DELETE trigger deletes the object, so dropping the clone would delete the other service's object).
- **Not copied, on purpose:** `auth_app.default_role_id` (the app is shared and has one default); the privileges of global roles. Privilege paths ignore developers, so copying them to the new path merged into the grant of a published service on the same path (`dev@/b` widened `/b`), and nothing removed them on DROP (found in the review of #85).
- **A clone has no relation with its source** (decision in the review of #85): a service role's privileges are copied as they are (one on the source's `host_ctx` gets the new path; a wildcard or another service's path stays), and that is safe only because the REST daemon applies a service role's privileges to that role's service alone (`AuthPrivilege::service_id` in rest-daemon's `rest_request_handler.cc`; upstream MRS matched every privilege by path and a cloned `*` privilege reached every service). Documented in `rest-daemon-5.0.md` §2a.
- **Deleting a service's roles:** `service_BEFORE_DELETE` deletes them in index order, which fails with 1451 on `mrs_privilege` when a role extending another has privileges. `delete_service()` calls `delete_service_roles()` (leaves first) before the DELETE. The `mrs_role` trigger's derived-role branch (`IF OLD.id <> NULL`) is dead on purpose: as `IS NOT NULL` it raises 1442 (a trigger can't delete from its own table). Don't "fix" it.
- **Role ordering:** `service_roles_parents_first()` serves `role_create_statements()`, `clone_service_roles()` and, walked backwards, `delete_service_roles()`.
- **Grants of a `dev@` service's roles** name the developers: `Role::specific_to_service_developers` goes through `format_developers()`.
- **Dump:** `SHOW CREATE REST SERVICE ... INCLUDING DATABASE ENDPOINTS` writes each service role's CREATE, parents first, followed by its `GRANT REST ... TO role;` without the role's service clause. A GRANT without a service applies to `*`, so a privilege on the service's own path (`service_path` = the service's `host_ctx`: host name + request path, no developers, the value the clone compares) is written `ON CURRENT SERVICE` (`privilege_grant_statement(..., current_service_host_ctx)`); wildcards and other services keep `ON SERVICE <path>`. The script then names the service only in CREATE and USE, and `mrs.load.service(as_path=...)` (mariadb-shell-plugins) rewrites only those two.
- **`ON CURRENT SERVICE`** (GRANT/REVOKE target, bison + ANTLR, keyword `CURRENT` also a name): `ON CURRENT SERVICE [SCHEMA p [OBJECT p]]` stores the current service's `current_service_host + current_service`, so it is the same row as `ON SERVICE /path`; no current service gives "No REST SERVICE specified.". `check_pattern` is skipped for it (a host_ctx with a host name does not start with `/`). Tests: `Mrs_parser.*`, `grammar_test.sql`, `mrs_auth_norecord.py` (grant/revoke, the error), `mrs_services_norecord.py` (the dump names the path twice; reloaded by changing CREATE and USE, the grants follow).
- **Tests:** `mrs_services_norecord.py` (roles, groups, auth app links and row security; the `dev@` clone on the same path; global roles never extended; dropping a clone leaves the source alone; the dump's GRANTs in order); `mrs_content_norecord.py` (content-set links to the copied scripts; links to other services).
- Only services on the empty host can be cloned (`find_service()` matches `h.name = ''`); `clone_service()` still rewrites privilege paths to `url_host_name + new path`, the `host_ctx` form they are stored in.
